# Round Robin product audit and decisions

Historical planning audit: November 15, 2026 • Baseline: product plan Version 5 • Planning result: Version 7

Current implementation status updated November 16, 2026; the historical audit below is not the current runtime audit.

## Judgment

Round Robin has a credible product idea: help an owner compare consequential options with evidence and independent review. Its strongest existing decisions are independent first answers, inspectable passages, visible disagreement, strict paid-work accounting and recoverable execution. Keep them.

The main weakness is the distance between a thorough technical plan and proof that a person can make a better decision at an acceptable cost. At audit time, the workspace contained five original Markdown files and no application code, package manifests, runtime, tests or deployment configuration. This is a complete audit of that historical planning surface, not a verified assessment of a working application. Usability, accessibility, security, reliability and model quality remained unverified by the audit.

**Current implementation status:** the durable application, provider/worker boundaries, evidence/report/export workflow, recovery/hosted controls and gated visual/native extensions now exist. The [fresh implementation audit](evidence/exhaustive-audit/REPORT.md) is the current runtime review and records the accepted final verification results; earlier [preparation](evidence/phase0-preparation.md) and [implementation](evidence/implementation-phases.md) records remain historical snapshots. The accepted local run does not claim hosted CI or release acceptance; unresolved upstream container advisories remain open.

The fresh work integrated one bounded corrective synthesis and independent re-audit without resetting original limits, immutable persisted claims and explicit selected-parent evidence/claim reuse, and atomic active-parent replacement under a fresh preflight and explicit version. These are no longer missing engineering integrations. They do not establish real-model defect correction, human passage support or decision usefulness. The [acceptance register](ACCEPTANCE_BLOCKERS.md) retains consented user research/comprehension, funded protocol comparison, held-out quality/economics, manual accessibility, hosted staging and visual demand/improvement gates. The historical findings below explain why those gates exist; they are not a claim that the workspace still contains only planning documents.

The decision is to build one excellent comparison journey, establish its value with real tasks, and earn each expansion. “Best” means useful decisions, understandable evidence, dependable control and acceptable economics; adding more agents or screens does not establish those qualities.

## Original scope and sequence

The core local release includes the draft, three-provider independent review through the selected protocol, deterministic cost comparison, private evidence retrieval, recommendation/readiness, saved history, linked changes, outcomes and web/Markdown/JSON/PDF reports. Hosted access requires the separate session, isolation, storage and retention gates. Any enabled debate path must satisfy its own failure and quality checks.

Keep the documented Python/FastAPI, Next.js, PostgreSQL and Celery/Redis stack. Consolidate dispatcher and reconciler into one service and build records around a concrete vertical slice. Replacing the transport with a custom queue during this revision would create another design project without proving user value. Do not add Kubernetes, a vector database, separate adviser services or a broad agent framework.

Defer billing/subscriptions, hosted user-supplied keys, teams, voice, arbitrary code execution, automatic memory, notifications and integrations. If faithful quote summaries cannot carry essential evidence, verified text-PDF extraction outranks image generation. Visual work starts in one demonstrated raster domain; interfaces and diagrams need their separate native checks.

The original work order was discovery/prototype → bounded provider comparison → durable saved comparison → selected real protocol → private evidence/calculation → accessible full workflow → integrated quality/recovery release → optional hosted pilot. The later explicit construction authorization changed build order, while the release evidence dependencies remain. The [delivery backlog](DELIVERY_BACKLOG.md) assigns reviewable outputs to each step. Do not treat the number of written documents or passing simulated tests as product progress.

## Historical second-pass contract findings

The first pass covered the product recommendations and phase-level work. Reviewing those seven resulting documents exposed contracts that developers would still have had to invent. Version 7 closes them in the [implementation blueprint](IMPLEMENTATION_BLUEPRINT.md) and synchronizes the product, failure, phase, backlog and visual plans.

| Missing piece | Decision and implementation consequence |
| --- | --- |
| Displayed settings were not bound to paid Start | Single-use ten-minute preflight with revision/configuration/input hashes; initial/resumption admission expiry; stale or double-consumed Start dispatches nothing |
| Intake could repeat after a successful step despite immutable step identity | One successful proposed-brief/question batch, followed by deterministic user confirmation/freeze; no model rerun |
| Search privacy relied on model rewriting; narrow attachment scopes could leak through synthesis | Explicit approved public term IDs/server query templates; one shared three-provider input scope; job-bound private asset downloads use a separate path |
| New/reused model claims lacked an identity-assignment protocol | Response-local aliases mapped atomically; child reuse manifests map approved immutable parent versions to child-scoped IDs without opening foreign access |
| Finish holds and rollover were not specified as accounting operations | Reserve once, convert into final-attempt reservations, use fixed lock order/UTC attribution and count unknown exposure once across periods |
| First paid experiment preceded the durable budget implementation | Exclusive runner lock, fsynced authorization journal, aggregate and batch limits, no automatic unknown-outcome restart |
| Expiring command records or indefinitely queued work could create surprise spending | Owner-lifetime minimal creating/paid command tombstones, explicit queue/input expiry and no automatic renewal |
| Readiness could inherit an unaudited model assertion | Deterministic reducer requires successful distinct audit for `ready_to_choose`, with explicit conditional/no-choice/null outcomes |
| Input/context and operations were qualitative | Bounded typed schemas and context assembly; explicit operator CLI, hosted OIDC/session approach, quotas, retention and timed restore profile |
| Research/funding blocked even offline preparation; repeats could inflate results | Offline sample/schema/prototype/simulator lane; 78 fixed-evidence trials with 13/16 primary-case gate; separate fresh 48-case end-to-end evaluation and executable deadline metrics |

The blueprint's traceability table maps each recommendation to a schema/API, module, essential proof and backlog/phase. The November 15 planning revision made no claim that these contracts had been implemented. Current implementation is recorded separately above. Live studies still require participants, preregistration and bounded funding; offline engineering evidence cannot replace those prerequisites.

## Prospective success criteria

These values are decisions to test, not measured achievements. Canonical definitions and change control live in the [product scorecard](PROJECT_PLAN.md#product-scorecard).

| Measure | Initial target |
| --- | --- |
| Blind decision usefulness | At least 13/16 primary feasibility cases and 39/48 fresh held-out cases score 4/5; no hidden critical defect in a qualifying result |
| First useful committed content | At least 90% of admitted ordinary-profile trials within 60 active seconds |
| Standard completion | At least 50% within 120 active seconds and 90% within 300; failed/cancelled/absent results count as misses |
| Paid run | Useful Standard result inside a provisional $2 USD authorization cap, including conservative unknown exposure |
| Personal aggregate authorization | Initially $10 USD/day and $50 USD/calendar month; hosted owner and deployment limits explicitly configured before paid access |
| Usability | At least four of five target users complete unaided and find the recommendation or why no choice is established, caveat, supporting passage and next action |
| Trust and control | No known hidden critical dependency, unauthorized disclosure, uncounted paid dispatch or false confirmed cancellation in release checks |

An 80% result from a small sample is a direction signal, not universal accuracy. Repeat use is measured when another real comparable decision occurs, rather than through daily engagement. User acceptance is distinct from factual correctness.

## Historical sources and limits

The audit read README, the complete product plan, failure register, implementation phases and visual workflow. Findings are traceable to their original sections: launch audience, first use, start a meeting, evidence quality, cost/performance, quality evaluation and Phase 0/2/8/9 gates. The revision preserves existing failure IDs and adds six specific requirements instead of claiming tests have passed.

The second pass read all seven Version 6 documents and added the blueprint. It expands assertions under the same 100 scenario IDs and 14 core combinations instead of inflating the catalog. Documentation structure/traceability checks do not establish runtime behavior.

External primary sources informed three narrow decisions. [Anthropic's engineering report](https://www.anthropic.com/research/multi-agent-research-system) describes multi-agent tradeoffs in its research product; Round Robin still needs its own matched evaluation. [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/) supplies the accessibility target. [OWASP's prompt-injection guidance](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) supports keeping authorization outside model instructions. None established application compliance or quality in the documentation-only audit, nor does it validate the later offline preparation.

Documentation verification checked local links/anchors, stable scenario IDs, phase allocation, counts, code fences and conflicting scope/limit statements. There was no runtime to exercise at audit time, and no paid provider calls, deployment, account changes or user outreach were part of the audit. Current runtime review and acceptance status are recorded separately above. The historical documentation-only audit is not reused as evidence that current runtime security, coverage or quality has passed.
