# Round Robin Failure Handling and Recovery

Version 4 • November 15, 2026 • Build-ready execution, privacy, decision and recovery contracts

Round Robin must preserve committed work, bound additional spending, and explain incomplete results when a dependency fails. This register defines obligations, code ownership and required proof. Following the user's November 16 authorization, the [implementation record](evidence/implementation-phases.md) tracks the durable handlers and actual PostgreSQL/Redis/worker, storage, recovery and browser checks now present. Exact assertions and remaining obligations stay in the scenario manifest. Passing selected engineering tests does not establish full scenario or phase acceptance, real-user comprehension or provider usefulness.

Use this document for execution and failure policy, the [product plan](PROJECT_PLAN.md) for product behavior and architecture, and the [implementation phases](IMPLEMENTATION_PHASES.md) for build order and test gates. The catalog covers the planned lifecycle and important combinations of failures. New integrations and unclassified failures require additional cases; a finite catalog cannot guarantee that every future failure has been anticipated.

The [product audit](PRODUCT_AUDIT.md) records the reasons for these changes; the [delivery backlog](DELIVERY_BACKLOG.md) turns them into prioritized work. This register remains the authority for failure invariants and scenario IDs. The [implementation blueprint](IMPLEMENTATION_BLUEPRINT.md) specifies payloads, transaction boundaries, bounded inputs and runtime configuration; implement its detailed contracts together with these assertions.

The [visual design workflow](VISUAL_DESIGN_WORKFLOW.md) defines the planned image generation, editing and image-review extension in Phases 7–9. Its limits are declared before starting that mode; they do not silently replace the text MVP's ordinary worker, deadline or upload defaults. The core invariants below also apply to visual work.

## When an API goes down during a meeting

| Dependency that fails | Required behavior |
| --- | --- |
| One model provider | Classify the error, attempt only an eligible bounded retry, and settle that work as unavailable if it fails. Keep its earlier valid contributions. Other providers continue only when the current stage remains eligible. Show the exact missing work and publish a limited result when useful. |
| Provider assigned to synthesis or audit | Use the single predeclared fallback to another configured healthy provider when eligible and funded. Record reassignment visibly. Audit must use a provider different from the successful synthesizer. If that cannot be achieved, save a deterministic partial report with synthesis or audit unavailable. |
| Every model provider | Stop scheduling calls that cannot succeed; do not spend the entire deadline polling. Preserve contributions and render a deterministic partial report without another model call. If nothing substantive survived, mark the run failed. |
| Search or a source website | Record failed retrieval; retain the exact support gaps. Continue only with explicitly conditional claims where useful. Never invent a source or mark a failed fetch verified. |
| Round Robin HTTP API | Workers can continue while PostgreSQL and their dependencies remain healthy. The browser shows its last confirmed state and reconnects. Stop is unconfirmed until a cancellation transaction commits. |
| PostgreSQL | No new paid authorization is possible. An already authorized call may finish; saving that same response is retried boundedly. Recovery checks original limits and fences. A response lost before commit can be unrecoverable and still billable. |
| Redis or dispatcher | Pending intentions remain in PostgreSQL. Reconcile and republish after recovery. Expired work is finalized without new model calls. |
| Export renderer or artifact storage | The saved report remains authoritative. Fail and retry only the export job; do not restart the meeting or call a model to regenerate it. |

For example, all three advisers may complete proposals and then Claude becomes unavailable during critique. Keep Claude's proposal, mark its critique/revisions unavailable, and allow the other two actual reviewers to continue. An objection against Claude's proposal remains unresolved if its author cannot answer it. The report must not imply that all three completed review.

## Rules that every handler must preserve

1. PostgreSQL owns run state, commands, attempt authorization, usage reservations, stage results, and ordered events. Redis transports identifiers; browser and Celery result state are not authoritative.
2. Persist a paid attempt's authorization, request count, conservative cost reservation, and execution fence before sending it. If this transaction cannot be confirmed, resolve its identity before sending anything.
3. External execution and billing are not exactly once. A lost response, crash, or ambiguous commit does not prove a request was free or never executed.
4. Permit one committed valid result per logical step. Its immutable key uses a role slot, not whichever provider services an attempt. Duplicate deliveries, expired workers, and role fallback cannot reset its call ceiling or replace its valid output.
5. Commit attempt outcome, retry-versus-settlement decision, validated output, usage reconciliation, stage state, events, and next work intentions atomically. A stage barrier closes once per recovery generation after all its scheduled work is committed or terminally settled. Retryable pending work cannot close a barrier as terminal failure.
6. Each retry, repair, fallback, and tool-related model follow-up consumes a real request slot and a separate reservation. The shared 24-call ceiling includes image/vision review and generation/edit submissions in visual mode; image work has additional submission and version limits. SDK retries are disabled. Queue redelivery itself is not permission to repeat a paid call.
7. Unknown usage remains visibly unknown and holds conservative exposure, even if an operator records a conservative accounting charge. It is never labeled provider-reported usage without evidence. Only evidence resolves the uncertainty; booking, lease expiry, period rollover and a new run do not refund or erase unresolved exposure.
8. Cancellation and deletion fence new authorization and result publication. A previously authorized external call may still start or incur charges; abort it best effort.
9. Separate transport availability, run status, decision readiness, current stage, participant coverage, evidence status, and usage status. An offline browser does not mean a failed meeting; a completed run does not establish that its user can choose an option.
10. A deterministic partial report uses saved records and application templates only. It can run after the model-work allowance expires; it cannot invent a new recommendation, successful review, source, or contribution.
11. Do not authorize work when ownership, configuration, schema compatibility, execution epoch, or spending headroom cannot be established. Unclassified exceptions settle affected work and escalate to diagnostics rather than entering an unlimited retry loop.
12. Every fault test checks stored state, upstream request count, spending reservations, public events, and user-visible recovery, not merely an exception type or HTTP response.
13. Every new paid authorization atomically checks per-run limits, per-owner and deployment daily/monthly exposure, and the spending kill switch. Charged amounts, unknown exposure and live reservations count without double counting, including sequential runs, follow-ups, retries, explicitly funded connection tests, billable retrieval, and later visual work. No fresh run identity resets aggregate limits.
14. Protect enough money, remaining inference call slots and admitted time for the selected protocol's mandatory synthesis and independent audit before optional work. In visual mode, protect required next-version reviews too. If this finish envelope cannot fit, skip optional work or finalize an honest deterministic partial report; protection is not permission to exceed another limit.
15. Draft editing and preflight perform no model inference. Start requires an unexpired preflight and expected draft revision, then snapshots its inputs/configuration once. One successful intake proposes the normalized brief and at most three questions; answers are incorporated and confirmed/frozen deterministically without rerunning intake. Deletion revokes input access and fences dependent work under the erasure policy.
16. Public search is an external recipient. Build queries only from explicitly approved public-term IDs and server templates, never freeform private model text or model-invented URLs. Core run content shares the same three configured provider recipients, including derived peer/fallback packets; do not promise narrower attachment scopes. Public evidence rejects credential-bearing URLs and no token reaches public diagnostics or exports.

## Admission, input and accounting boundary contracts

### Preflight, intake and recipient scope

Preflight is a no-inference server snapshot of the draft revision/hash, selected ready attachment IDs/hashes, approved public research terms, shared provider recipients, protocol, model/prompt/configuration/pricing versions and limits. It expires ten minutes after creation. Start supplies `preflight_id` and the expected draft revision; stale, changed, expired or foreign preflight fails without creating paid work. Intake answers may resolve the declared brief, but cannot widen recipients, mutate selected bytes or silently raise limits.

Consume preflight atomically with one unique run: a different command UUID cannot spend twice from the same preflight. Same-command replay resolves its original result; intentional repetition needs fresh preflight. Its ten-minute validity is checked only before accepted Start. Distinguish intake-resolvable missing options/details from ownership, price, scope and structural blockers; require two to four confirmed options before proposals.

Initial queue admission expires 30 minutes after accepted Start, with the exact `not_after` shown in preflight/acceptance. Check this gate only until `first_admitted_at` is set. An expired first admission settles from saved records with no new inference; continuation needs a new explicit authorization. An intake input request expires after 24 hours. Confirmation/retry requeues an already-admitted run under its own eligibility and original remaining active time, not the already-satisfied initial queue deadline. Late input cannot revive expired work. Check frozen configuration at admission and every dispatch; stale model, scope or pricing configuration blocks authorization rather than silently substituting current settings. Recovery never resets these bounds.

Accepted clarification confirmation or an eligible manual retry creates one 30-minute resumption-admission ticket bound to its command identity. Replays cannot renew it and expired tickets never continue automatically. Reuse the existing finish pool, active intervals and step/call counters. Test first admission after 20 minutes, two hours awaiting input, then valid confirmation/requeue: neither preflight expiry nor the old initial deadline incorrectly blocks it, and no allowance resets.

A successful intake returns one proposed normalized brief and at most three questions. After the user answers or confirms the conditional assumptions, application code creates the confirmed brief revision and freezes it. Do not call intake again under a new role/step to continue questioning. A malformed or failed intake may use only its original step's second actual call. Decisive gaps lead to an explicit conditional scope, insufficient evidence or no dependent work, rather than an endless clarification loop.

For core runs, every selected input must permit the same configured OpenAI/Claude/Gemini recipient set. A narrower attachment permission fails preflight rather than leaking through a peer summary, synthesis or fallback. Derived contribution packets use that shared scope. Public research is separate: the user explicitly approves public terms; the server constructs queries from term/template IDs. Advisers select IDs rather than supplying freeform query strings or fetch URLs. Fetch only registered discovery/source candidates or explicitly approved user URLs through the controlled fetcher. When approved public terms are insufficient, retain the evidence gap or request new approval; do not infer that private context is public.

Public evidence fetching rejects credential-bearing URLs. A signed provider-result URL is a distinct private adapter operation bound to an authorized owner/job and allowlisted provider hosts, with destination/redirect/size checks; its token never enters search, rendered links, logs or exports. This exception does not authorize arbitrary signed URLs as public research evidence.

Temporary uploads become usable only after bounded validation, ownership/meeting checks and an immutable ready-state commit. Start binds the exact server-computed normalized-byte hashes; client hashes/storage keys are not authoritative. Apply blueprint input/context limits before authorization, preserve hard requirements and recipient scope, and reject overflow that cannot be represented faithfully. A new object or context hash cannot reset the same logical step's call counter.

### Spending windows, finishing resources and lock order

At first admission, reserve the selected protocol's finish-money pool once against run, owner and deployment policy. Reacquiring admission after input/retry reuses its remaining hold. When a final-stage attempt is authorized, atomically transfer its allocated hold into that attempt's reservation; do not add the same money twice or silently discard aggregate headroom. Protect remaining finish inference slots and bounded critical-path time too. Optional work may use only the unprotected remainder. Declared fallback/correction work still requires its own remaining allowances and conservative bound.

For any outstanding/unknown operation, exposure is at least the greater of its conservative authorized bound and any higher reported amount; never clip a higher actual charge to the configured cap. Trusted final provider evidence permits an explicit reconciliation adjustment. Count each operation/unused finish hold once per applicable policy window, not once as a hold and again as a reservation or conservative booking. All spending paths lock in the same order: deployment policy/buckets, owner buckets, run, then step/attempt. Cancellation, limit updates and kill-switch changes use compatible ordering and versions.

Settled charges belong to their immutable UTC authorization periods. Outstanding reservations/unknown exposure carry into active daily/monthly aggregates conservatively and exactly once until evidenced settlement. An operator may conservatively book a charge for accounting, but an unresolved charge still carries after midnight/month rollover; booking alone cannot wash it out of the current spending check. Preserve adjustment identity/history across restarts and restore. Attempt exposure is not refunded merely because a run, provider slot, command or lease expires. Release only demonstrably unused finish holds through explicit deterministic terminal settlement; this never clears an uncertain attempt.

Phase 0's runner has a single-process lock and a journal flushed and synchronized before every send. It enforces explicit batch request/currency ceilings and aggregate spending policy before the first paid operation, in addition to per-trial/step bounds. A second runner cannot share the same budget journal concurrently. A lost response or crash leaves an unknown operation; restart never automatically retries that uncertain operation or creates a new journal to obtain fresh allowance.

### Command lifetime, ownership and erasure

Keep minimal creating/paid-command tombstones for the authenticated owner's lifetime: command UUID, keyed canonical body hash, committed outcome and noncontent resource references. Replaying a deleted resource's command returns gone without creating or scheduling anything. Compact autosave records only when revision compare-and-swap still rejects old effects. Account deletion and a later new account use separate authenticated owner namespaces; old pending browser commands cannot replay into the new account. Never retain a plaintext question or attachment in a command tombstone.

MVP follow-ups stay within the same owner-scoped meeting. A child reuse manifest maps child-scoped IDs to selected immutable parent versions/hashes, with provenance and freshness checks. Models use child IDs; broad parent-ID access stays invalid. Physical immutable bytes may be shared within the meeting without relying on a mutable parent output. Whole-meeting deletion fences/purges the entire lineage. Retention never removes paid-command deduplication guarantees or unresolved accounting. Hosted startup fails closed when authentication, funding, private storage, retention or owner/deployment resource quotas are missing. Development identity requires explicit development mode, loopback binding and rejection of external/proxy exposure; a public proxy must not activate local identity.

## State and stage decisions

### Run transitions

| Current state | Allowed transition and condition |
| --- | --- |
| `queued` | `running` after admission and invariant checks; require the initial queue deadline only before first admission. Already-admitted input/retry continuations retain their own eligibility and original active allowance. `cancel_requested` after confirmed Stop; terminal failure/limited status when work is expired/ineligible, with no new inference. |
| `running` | `awaiting_input` for intake clarification; `cancel_requested`; or a terminal state after stage completion, limits or failure. Waiting for a provider stays `running` with explicit attempt status. |
| `awaiting_input` | `queued` after a valid expected-version clarification within its 24-hour input window; `cancel_requested` after Stop; terminal failure/limited status after expiry. Answers deterministically confirm/freeze the one proposed intake brief. No dependent paid work runs while input is outstanding. |
| `cancel_requested` | `cancelled` after pending work is fenced and a partial-report intention is saved. Never return to ordinary execution. |
| `failed` or `completed_with_limitations` | `queued` only for an eligible explicit synthesis/audit execution retry with unchanged inputs, original remaining allowances, a spare paid call and a spare infrastructure claim. |
| `completed` or `cancelled` | No automatic revival. New model work uses an explicit linked follow-up with fresh limits. |
| Any state with a deletion tombstone | Deny new access/work/reuse; purge all meeting-owned content. Deleted meetings cannot create follow-ups. |

Before confirmed cancellation, a Stop command can be unknown to the server. After confirmation, report generation and usage reconciliation may finish without new model spending. New follow-ups do not alter their parent's terminal state or saved report.

Use the logical key `(run_id, stage, round, stage_iteration, role_slot_id)`. Independent/adviser slots bind to their configured provider; moderator slots such as synthesizer and auditor stay stable if an attempt uses a declared fallback. Record actual provider/model on each attempt. A fallback cannot create a new logical step with another two-call allowance.

Start `recovery_generation` at zero. An accepted manual retry increments it, retains the same logical step and its accumulated claim/call counters, and reopens only the failed synthesis/audit evaluation and necessary dependent work. Reuse immutable successful prerequisites. Barrier closure and successor intents are unique for `(run, stage, round, stage_iteration, recovery_generation)`; previous closures remain historical. This permits a new report after successful recovery without reopening proposals or replaying earlier successors. Reject commits from older recovery generations except permitted usage reconciliation. `stage_iteration` still changes only for substantive correction/re-audit.

### Coverage and publication

Record outcomes per run, stage, round, step and actual provider: pending, succeeded, failed, skipped or not required, plus the committed output reference. These are step outcomes, not additional run statuses. `outcome_unknown` describes a possibly executed attempt; it never counts as a successful contribution.

| Stage or outcome | Decision |
| --- | --- |
| Independent proposals | Require at least two validated proposals from distinct configured providers for comparative review. Zero or one ends comparison and preserves a partial result. |
| Critique | Require two distinct actual reviewers for a completed debate cycle. Earlier proposals do not count as reviews. If coverage drops below two, stop further debate and preserve the interrupted-review limitation. |
| Revision | Each assigned material objection needs an actual author response or an explicit unresolved disposition. No objection means no fabricated revision is required. Another adviser cannot impersonate the absent author. |
| Synthesis | A validated structured draft must reference saved claims, evidence and objections. Missing synthesis yields a deterministic partial report. |
| Audit | The reviewer must differ from the successful synthesizer. An unavailable independent audit remains a limitation; agreement from earlier stages does not replace it. |
| `completed` | The selected protocol and publication checks finished with required coverage and no material execution failure or hidden evidence limitation. A disclosed conditional, insufficient-evidence or no-feasible-option conclusion can be complete work. Ordinary acknowledged dissent can remain; readiness is separate. |
| `completed_with_limitations` | A useful substantive result survives, but required participation, evidence-check work, synthesis or independent review is incomplete and visible. If no validated recommendation exists, set it to `null` with an explicit unavailable reason. |
| `failed` | No useful substantive output survives. Save a deterministic failure/status report when storage is available. |
| `cancelled` | Confirmed user cancellation takes precedence over ordinary completion; late output cannot change the conclusion. |

### Decision readiness

Store `decision_readiness` separately from run completion and render it consistently in Overview, saved reports and every export. Use `ready_to_choose`, `conditional`, `no_feasible_option`, or `insufficient_evidence`, with reasons and essential dependency references. Before there is a validated assessment, use a null readiness value with an explicit pending/unavailable reason. A missing recommendation is `null` with an unavailable reason; a partial renderer cannot infer one from agreement or an earlier proposal.

Evaluate hard requirements individually as `pass`, `fail`, `unknown`, or `not_applicable`, preserving their basis and explicit reasons for nonapplicability. Publish `ready_to_choose` only with valid synthesis, a positive audit from a distinct provider, all selected-option hard requirements passed or justified not applicable, and inspectably supported essential dependencies. Missing/negative audit cannot produce ready status; preserve review-incomplete/critical-defect reasons and conditional or insufficient-evidence status as appropriate. A known failed hard requirement blocks ready status. Claim `no_feasible_option` only when the considered options have established disqualifications; unknown feasibility alone is insufficient. Application reference/constraint checks validate stored relationships, not the truth of every passage or model judgment. Neither agreement nor completion overrides these rules.

After every scheduled step settles, evaluate the barrier inside a transaction. Settling one participant's failure is necessary even when its response is absent. Never leave the stage waiting for an output that will not arrive. If storage is unavailable, recovery persists this decision after reconnection; the application cannot claim a report was saved meanwhile.

## Retry and timeout policy

These are initial configuration choices to verify in fault tests, not measured availability promises. Persist their version with the run. This table describes the text MVP and ordinary model-call workers, including later vision-review calls. The visual extension's declared image-worker, upload and run-time differences are specified below and in its canonical workflow. Lower remaining request, spending or active-time limits always take precedence.

| Control | Initial decision |
| --- | --- |
| Provider calls per logical step | At most two actual calls total, including automatic retry, one schema repair, manual execution retry or role fallback. These are competing uses of the second call, not separate allowances. |
| Total calls and active time | At most 24 model calls across all modalities. Text mode allows 600 admitted active seconds per run; the explicitly selected visual mode allows 1,800. Queue and user-input waits are excluded from active time but bounded by the separate admission/input expiry. Admitted retry/capacity waits and asynchronous generation waits are included. |
| Preflight and waiting bounds | Preflight expires after ten minutes; initial admission after 30 minutes from accepted Start; user-input wait after 24 hours. Expiry never authorizes a fresh call, resets counters or refunds uncertain usage. |
| Ordinary model-call deadline | Minimum of 90 seconds, remaining run active time, and remaining task soft time minus 20 seconds for persistence and five seconds for cleanup. If insufficient, yield/settle without authorizing. No open-ended stream. |
| Transient retry | At most one; default wait two seconds plus zero-to-one-second jitter. Honor a longer valid `Retry-After` only when it fits remaining time. Otherwise settle unavailable. |
| Same-response persistence | At most three persistence attempts within 20 seconds; verify ownership/fences before each. No repeat provider call just to save a response. |
| Database transaction conflict | At most three fresh transaction attempts for known retryable conflicts. Ambiguous commit is resolved by operation identity before any retry of its effects. |
| Circuit breaker | Three consecutive transient failures for the same configured provider/model/credential version within 60 seconds open its circuit for 30 seconds. One later funded request may probe; no paid health probes. |
| Ordinary worker execution | One upstream call per task; a second call uses separately scheduled work. Ten-second heartbeat; 150-second execution lease; soft task limit 115 seconds and hard limit 120 seconds. Capacity/DB waits must leave room within the task envelope for that call and bounded persistence, or yield without sending. Synchronous image generation uses its separately declared worker envelope. |
| Infrastructure recovery | Reconciler checks approximately every five seconds; at most three execution claims per logical step. Claims and paid-call counts are separate ceilings. Excess claims settle terminal failure rather than loop. |
| Ordinary Redis visibility | Start at 180 seconds, greater than the ordinary task hard limit. Database ownership and reconciliation remain authoritative even if redelivery happens sooner or later. The synchronous-image queue uses its separate visibility limit. |
| Browser recovery | SSE heartbeat every 15 seconds; after 45 seconds without contact show a connection warning. Fall back to state/event reads with capped backoff, initially five seconds up to 30 seconds. |
| Personal capacity | One executing meeting, three locally authorized/in-flight model attempts globally and at most two per provider. Unknown remote work may outlast a slot; its exposure remains accounted for. |
| Aggregate spending | Deployment-configured owner and deployment daily/monthly ceilings apply to charged amounts, unresolved exposure and live reservations across all paid entry points. Count each exposure once. Period rollover does not erase outstanding unknown exposure; reserve atomically against every applicable ceiling and kill-switch state. |
| Finish envelope | Before optional research, critique, repair or another image candidate, retain the mandatory synthesis/audit and required visual-review money, call slots and time. Bound optional calls by the remaining deadline minus finish time; stop optional work when any dimension cannot fit. |
| Hosted resource quotas | Configure owner/deployment storage, pending-run/work, event retention and export-job quotas before hosting. Reject new excess work accurately and clean temporary/orphaned objects; never delete retained user history silently. |
| Search and fetch | Six queries and eight fetched pages per run; initial per-query timeout ten seconds, fetch timeout 15 seconds, at most three redirects and two MiB decoded body per page. Bound wire and decoded reads and enforce the remaining run allowance. |
| Text MVP uploads | Plain UTF-8 text and Markdown only; at most one MiB per file, five files per meeting. Validate type/content and apply a combined five-MiB limit. Freeze selected IDs, immutable hashes and recipient scope per run. New attachments do not enter a frozen run. Whole-file retry is sufficient initially. Raster references require the separately gated visual upload capability. |

Celery late acknowledgments and worker-loss behavior require explicit configuration; late acknowledgment alone does not cover every terminated-worker case. Configure and test `task_acks_late`, `task_reject_on_worker_lost`, time limits, prefetch and broker visibility together. Keep retry due times in PostgreSQL rather than long broker countdowns. [Celery tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html), [Celery Redis delivery](https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/redis.html).

### Visual extension limits

These are gated visual-mode obligations. Their implementation and actual checks are tracked in the [implementation record](evidence/implementation-phases.md); the [visual workflow](VISUAL_DESIGN_WORKFLOW.md) remains authoritative. Disabled-by-default code does not constitute funded-provider or visual-quality release evidence.

| Control | Visual-mode decision |
| --- | --- |
| Versions and submissions | V1 plus at most two intentional edits, V2 and V3. At most four dispatched generation/edit attempts per run, including rejected, failed, ambiguous and retried submissions whether charged or not; at most two per stable step. A retry cannot become a new version merely to reset a counter. |
| Shared spending and calls | Generation/edit submissions, vision reviews and other model invocations share the 24-call ceiling and monetary limit. Reserve the next required reviews before authorizing generation. All actual charges and unknown exposure remain accounted for; an image-specific cap adds no spending entitlement. |
| Admitted time and concurrency | At most 1,800 admitted seconds, declared before Start, and one locally active image-generation job across the application. Provider-side execution may remain unknown after a timeout; its reservation stays held. Polling, external job waits and retries do not pause the admitted clock. |
| Async provider jobs | Use submit/poll/retrieve only when the API supports recoverable job identity and those operations. Persist its job ID; a queue around a synchronous endpoint does not create those guarantees. At most 60 read-only status polls per run. Status/download reads do not use inference slots; any operation starting inference does, regardless of billing, and all charges enter the ledger. |
| Synchronous image worker | Use a separate queue and isolated broker namespace/database: call timeout `min(600 seconds, remaining admitted run time, remaining task soft time minus 25 seconds)`, soft limit 630, hard limit 660, lease 720, heartbeat ten and visibility 900 seconds. Consumers sharing a namespace need consistent visibility; separate queues alone do not isolate transport settings. Reserve 20 seconds for persistence and five for cleanup. Never use an ordinary 120-second task for a long image call. |
| Raster references | Only after the visual upload gate: PNG/JPEG, at most ten MiB and 16 megapixels per input, at most four reference images. Enforce decoded dimensions/memory limits, canonicalize safely, strip EXIF/location metadata and keep source/canonical assets private. Generated outputs also require bounded validation. |
| Image-review coverage | Two distinct vision-capable critic providers must review the same immutable version, and both must differ from the actual generator provider when known. Generator self-critique is supplemental. Review-only mode still requires two distinct critics; disclose unknown generator provenance rather than claiming independence from an unknown generator. Server-bound receipts identify supplied pixels/hash and transformations; model-repeated hashes do not prove inspection. |

Poll/download work has its own stable operation identity and bounded recovery; it does not reset or consume the generation step's paid-submission allowance as though it were a new generation. A poll that actually invokes model inference must pass shared call and budget authorization. A later native UI/code renderer requires its separate isolated-execution gate; the image extension does not authorize arbitrary code execution.

### Error classes and fallback

Classify provider failures by normalized structured code and send/usage certainty. Retry rate limits, temporary service errors and incomplete transport only within the second-call allowance. Authentication, exhausted provider credit, inaccessible models, invalid configuration and explicit refusals do not get same-provider automatic retries. A refused answer is not malformed JSON. A valid but unhelpful answer does not justify an automatic retry loop.

For context overflow, rebuild a bounded context packet once without changing the frozen brief, removing essential dependencies, or exposing peer proposals during independence. Any resubmission consumes the second call. For a schema-invalid response, one repair may use that same remaining call. Validate cross-references and semantic requirements after schema validation.

At run creation, record an ordered fallback list for moderator tasks such as intake, evidence review, synthesis and audit, drawn only from the user's configured participants. One role reassignment may consume the second call when the original provider is unavailable. Record the original failure, actual provider/model, inputs and reassignment event. Keep audit distinct from synthesis; if no suitable reviewer remains, publish a limited report. Independent proposals, critiques and author revisions do not switch providers or count duplicates as diversity. A refusal does not trigger fallback to evade the refusal.

Manual execution retry keeps the same logical step key and creates the next attempt; it cannot reset the two-call ceiling or original run limits. `stage_iteration` changes only for the single allowed substantive correction/re-audit cycle, which preserves previous valid outputs and is independently counted against the 24-call ceiling.

## Code flow to implement

This pseudocode describes control boundaries. Transaction helpers must also enforce ownership, expected versions, deletion, deployment epoch, admission, circuit, request counts and conservative budget limits.

```text
execute_step(step_id):
    claim = claim_step(step_id)                 # bounded claim; new ownership token
    if already_committed_or_ineligible(claim): return
    packet = prepare_validated_frozen_inputs(claim)
    attempt = authorize_attempt(claim, packet)   # transaction: run/aggregate limits + kill switch + finish reserve + input scope + count + fence
    if authorization_commit_is_unknown:
        resolve_authorization_by_attempt_id()   # send nothing until confirmed
        if cannot_resolve_safely: return

    outcome = provider_generate_once(packet, attempt.deadline)
    normalized = validate_or_classify(outcome)   # refusal, malformed, unknown usage, etc.
    persist_received_result(attempt.id, normalized):
        transaction:
            recheck_owner_run_epoch_recovery_and_input_erasure_fences()
            reconcile_identifiable_usage_idempotently()
            if run_cancelled_deleted_terminal_expired_or_stale:
                reject_content_and_record_permitted_late_metadata()
            else if retry_or_repair_is_eligible:
                save_attempt_outcome_and_keep_logical_step_pending()
                enqueue_same_step_retry_intention()  # next task, not an inline call
            else:
                commit_valid_output_or_terminal_step_failure()
                if all_stage_work_is_settled:
                    close_current_generation_barrier_once()
                    enqueue_successor_or_report_finalization_intention()
            append_ordered_events()

    if persistence_outcome_is_unknown:
        resolve_by_stable_operation_id()        # do not assume rollback
    if response_was_lost_before_commit:
        reconcile_unknown_attempt()            # reservation remains held
```

Only the same surviving executor that knows it has not sent a request may send after confirming an ambiguous authorization commit. A replacement executor treats an existing authorized attempt as potentially sent. No catch-all handler should blindly retry `execute_step`. An unexpected error first records or reconciles the attempt, then settles work under the explicit policy. If database access is unavailable, stop dispatch authorization and let the reconciler recover saved intentions later.

## Command and connection recovery

Use a stable client-generated command UUID as the idempotency identity, scoped to the authenticated owner. Persist its keyed canonical body hash and saved result in the command transaction; retain the minimal creating/paid-command tombstone for the owner lifetime. Same identity/body returns the original result; a changed body conflicts; replay for a deleted resource returns gone without work. Add `GET /api/commands/:command_id` for owner-scoped outcome lookup after a lost response or refresh. A lookup with no record does not prove an in-flight command cannot still commit; replaying the same identity remains the safe recovery, subject to the original preflight/expiry and resource outcome.

Draft edits before Start use ordinary owner-scoped, versioned application writes without model inference or provider connection probes. Start checks the expected draft revision and freezes its selected inputs in the accepted command transaction. A concurrent edit either wins before that snapshot or receives a stale-version conflict; it cannot silently enter already authorized work.

Keep only nonsecret pending-command metadata in browser persistence. After reconnect, read the command and run before offering another paid action. After reauthentication, reconcile first and require a user action for any still-pending paid command. Do not silently submit a new command UUID.

Errors include `code`, sanitized `message`, `correlation_id`, `retry_scope`, optional `retry_after_seconds`, and whether state/commit outcome is known. Retry scope distinguishes a read, the same command, an eligible failed stage, an export, a linked follow-up or no retry. A generic Retry button must not conceal which action it repeats.

SSE replays committed run/sequence IDs; the client deduplicates. When a cursor or supported event version cannot be used, fetch a consistent meeting snapshot with an event cutoff and then replay after it. Never advance the cursor past an unapplied event. Authentication failure stops reconnect storms; it is distinct from ordinary network loss. SSE IDs and reconnect fields are transport features; saved replay is an application responsibility. [SSE format and reconnection](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events).

## Combined failures and invariant testing

Testing each row alone is insufficient. Exercise every boundary before authorization, after authorization, after provider acceptance, after response receipt, during commit, after commit before acknowledgment, and after scheduling the next step. Use deterministic fault hooks and actual process termination at the relevant boundaries. The fourteen core combinations below remain required; additional image-job, version, critic and asset combinations are specified in the [visual design workflow](VISUAL_DESIGN_WORKFLOW.md).

Add state-machine tests that generate valid and invalid interleavings of start, claim, authorize, return, commit, retry, cancel, delete, lease expiry and restart. In every generated trace assert uniqueness, fences, bounded counts/exposure, immutable versions, correct coverage and absence of deleted/foreign content. Seed and retain a regression fixture for every discovered production-like failure.

## Operator recovery procedures

### Provider outage

Inspect normalized error, circuit state and configured credential/model without logging secrets. Stop only the affected work, let eligible healthy participants finish, and verify the report's actual coverage. Provider recovery permits an eligible explicit retry only under the unchanged valid frozen configuration and original allowances. A changed model, scope or pricing configuration requires new preflight and an explicitly linked run; it cannot rewrite failed participation. Provider recovery does not automatically reopen a terminal meeting.

### Database or broker outage

Restore database connectivity before enabling new paid work. Inspect commands, current fences, active intervals, unresolved attempts, reservations and pending outbox rows. Resolve ambiguous commits by identity. Reconcile expired leases, then restore broker/dispatcher delivery. Never bulk-mark attempts free, clear all reservations, delete pending intentions, or replay every broker message as fresh work.

For unresolved charges, inspect provider evidence when available. An operator may conservatively book the held bound through an explicit idempotent accounting record with reason, evidence and timestamp, without claiming provider-reported usage. This cannot settle uncertainty or remove active-window carry without evidence: the same operation remains conservatively counted once rather than both reserved and booked. Reconciliation adjusts only evidenced differences and retains the original uncertainty history. Period rollover cannot erase unresolved exposure. The spending kill switch prevents new paid authorization after its transaction commits, while previously authorized requests may still execute or bill. Resume only after accounting, applicable owner/deployment ceilings and input/fence checks pass.

### Deletion durability

Authenticate and check ownership before accepting deletion. Write an idempotent noncontent deletion intent to a durable manifest managed outside the database snapshot being backed up. Then atomically tombstone/fence the meeting, save the purge job and command outcome in PostgreSQL. Acknowledge successful deletion only after the external intent and database transaction are confirmed durable. If either acknowledgment is lost, reconcile the same command/intent; an accepted deletion may continue even while its client sees an unknown outcome.

The manifest stores only deletion/meeting identifiers, execution epoch and required timestamps, with restricted access. A crash after prewriting the manifest but before the database commit leaves an authorized pending deletion that the reconciler completes. Backup procedures retain the manifest separately and establish its completeness through the latest acknowledged deletion. If restoration cannot establish that completeness, keep user access and workers disabled. Test every write/acknowledgment boundary; a manifest copied only inside the database backup cannot protect newer deletions.

### Backup restoration

Start with workers/dispatcher disabled and user access closed. Advance the deployment execution epoch and isolate old processes/broker messages. Establish the complete deletion manifest from outside the restored application snapshot and purge tombstoned content before access; missing or incomplete manifest keeps recovery closed. Quarantine restored active/pending runs; reconcile external usage and the ledger where possible. If accounting cannot be established, retain uncertainty and disallow automatic continuation of those runs. Read historical reports safely, then permit explicitly authorized new work only after the recovery gate passes.

Disconnection does not prove a database operation rolled back, and restoring an earlier database state can remove later accounting records. These boundaries motivate identity-based commit reconciliation and the restore gate. [PostgreSQL connection termination](https://www.postgresql.org/docs/current/protocol-flow.html#PROTOCOL-FLOW-TERMINATION), [PostgreSQL recovery](https://www.postgresql.org/docs/current/continuous-archiving.html).

### Unknown failure

Stop affected paid scheduling, preserve last confirmed records, record a sanitized correlation ID, and render a partial/status report only from available committed data. Reproduce the condition in a disposable environment and add its scenario and regression test before enabling automatic recovery. The system must prefer an honest interrupted result over inventing a successful outcome.
