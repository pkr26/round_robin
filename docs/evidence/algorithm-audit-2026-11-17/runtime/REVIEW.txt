RUNTIME-01 [P1] Optional retry waiting can consume the protected synthesis and audit time
Source: backend/src/round_robin/orchestration/policies.py:88-93
Trigger: A proposal fails with a valid long Retry-After while the other two independent proposals succeed.
Observed: plan_recovery checks only wait + 30 seconds. A 500-second wait is accepted within the default 600-second allowance although 190 seconds are reserved for synthesis/audit. The proposal barrier remains open. At the accepted retry time the failed proposal is skipped and synthesis immediately fails finish_time_reserve before making any model call.
Impact: A run with sufficient useful proposals loses both mandatory final stages because optional backoff was allowed to spend protected finishing time. No recommendation is published.
Recommendation: Compute retry eligibility from the same mandatory-stage time reserve used by authorization and request construction. If wait plus the proposed request envelope plus persistence and still-required final work cannot fit, settle the optional proposal immediately and advance with the other two. Add a deadline-triggered barrier cutoff so previously scheduled backoff cannot consume the reserve.
Evidence: probe-results.json:retry_wait_consumes_mandatory_finish_time

RUNTIME-02 [P2] At-least-once duplicate execution bypasses Retry-After
Source: backend/src/round_robin/worker/tasks.py:94-139
Trigger: A worker saves a retryable failure and its future outbox intention; an older duplicate message for the same Step is delivered before that intention is due.
Observed: Retry eligibility is represented only by Outbox.due_at. execute_step sees status=pending and immediately authorizes another call. The probe's requested wait was 120 seconds; the second provider invocation occurred about 0.012 seconds later and consumed the last allowed call.
Impact: Provider Retry-After is not an execution invariant. Expected duplicate delivery can exhaust retries during a rate-limit period, reduce discussion completeness, and amplify provider pressure.
Recommendation: Persist a step/attempt not-before timestamp or retry generation, enforce it under the step lock before authorization, and carry the generation in delivery identifiers. Keep at-least-once delivery harmless across retry state transitions.
Evidence: probe-results.json:retry_after_bypassed_by_duplicate

RUNTIME-03 [P2] Clarification and manual retry bypass queue quotas
Source: backend/src/round_robin/api/events.py:242-253
Trigger: An owner already has the allowed three queued runs and confirms an awaiting-input run (or requests an eligible retry).
Observed: Only initial Start counts queued work. The resumption endpoints set queued and issue a ticket without checking owner/global queue counts. The direct clarification probe increased the owner's queue from three to four with a configured limit of three.
Impact: The documented owner/global admission backlog bounds are not maintained across all enqueue transitions, weakening fairness and overload protection. This does not bypass single-executing-run or monetary limits.
Recommendation: Apply one owner/global queue-capacity guard under the existing policy lock to every transition into queued, including clarification and retry; leave the resumable state intact when capacity is unavailable.
Evidence: probe-queue-results.json
