RR-018 [P1] Waiting runs multiply scheduler records and saturate dispatch
Location: backend/src/round_robin/orchestration/controller.py:279-281
Trigger: Keep a queued run waiting for admission, for example during a normal deployment drain or while another run is running, and run the normal reconciler and dispatcher loops.
Finding: Whenever admission waits, advance_run unconditionally inserts a new advance Outbox record. The one-second reconciler invokes this path independently, and a delivered advance invokes it again. Meanwhile, the previously delivered record remains published as long as the run is queued, so reconcile_once republishes it after 15 seconds. A successfully consumed timer therefore leaves behind both a replayable predecessor and a successor. One valid queued run under supported operator draining produced 2,781 outbox rows and 2,689 successful advance deliveries in 90 seconds, with 2,031 still pending; no message loss occurred. By 60 seconds duplicate advance deliveries saturated the default 50-record dispatch batch. This wastes database transactions, repeatedly takes the global deployment-policy lock, grows the persistent scheduler table, and delays useful work sharing the dispatcher and worker queues. The same insertion branch is used when another run occupies the single admission slot.

A supported draining policy keeps admission closed. A synchronous fake broker executes and commits every delivered advance; no Redis or provider network request is made. The clock advances in one-second increments and each tick calls the production reconcile_once and dispatch_once functions with their normal batch limit.", "observed": [{"seconds": 15, "outbox_rows": 40, "successful_deliveries": 23}, {"seconds": 45, "outbox_rows": 517, "successful_deliveries": 470}, {"seconds": 60, "outbox_rows": 1251, "successful_deliveries": 1189}, {"seconds": 90, "outbox_rows": 2781, "successful_deliveries": 2689, "pending_rows": 2031}], "cleanup": "The random PostgreSQL schema was dropped. Fix direction: Use a unique active advance intention per run/generation, and reschedule or upsert that intention when admission waits. Make consumption/recovery distinguish the already-handled intention from a genuinely lost delivery so predecessor and successor records cannot both be replayed. Keep the same invariant for reconcile-triggered and broker-triggered advancement.
Limits: The exact growth rate was measured with deterministic time and a synchronous successful sender; real broker throughput changes the rate. Queue amplification and batch saturation are directly observed. Delay to a separate real user request is an operational implication, not a separately measured latency result.

RR-019 [P1] Concurrent deletion can fail a normal backup and close all writes and dispatch
Location: backend/src/round_robin/operations/recovery.py:168-172
Trigger: Delete and purge a comparison after backup has captured its database rows but before it reads the export file.
Finding: The database snapshot is closed before referenced files are copied, with no shared lifecycle lock or retained-file lease. A normal meeting deletion followed by cleanup can therefore remove an export that the snapshot still marks ready. The backup then raises FileNotFoundError, deletes the unpublished temporary backup, and intentionally records backup_failed, persistently closing writes and dispatch across the deployment. The defect is the uncoordinated database/filesystem snapshot; the fail-closed durability response is intentional. Daily backup instructions do not require stopping services.
Evidence: {"probe": "probes/backup_race.py", "result": "evidence/backup-race-result.json", "observed": {"ready_before_backup": 200, "export_exists_before_backup": true, "delete_status": 200, "cleanup": {"expired_uploads": 0, "expired_exports": 0, "interrupted_exports": 0, "orphaned_export_files": 0, "deletion_records_reapplied": 1, "provider_requests": 0}, "export_exists_after_cleanup": false, "backup_outcome": "FileNotFoundError", "ready_after_backup": 503, "readiness_reason": {"status": "not_ready", "reason": "durability_compromised"}, "backup_published": false}, "method": "Real ready export API; deterministic legal DELETE + maintenance interleaved after the database snapshot; temporary SQLite/artifact storage only."}
Fix direction: Coordinate artifact snapshotting with deletion/retention, for example using a shared lifecycle lock, immutable retained references, or a snapshot/purge protocol. Reconcile legitimately deleted records consistently before publishing a backup; do not merely suppress missing-file errors or weaken the durability gate.
Limits: No corrupted published backup, data resurrection, or lost original report was demonstrated. The broad impact is the observed persistent write/dispatch gate after the race.

RR-025 [P2] Expired terminal retries retain unused finish funds and block new runs
Location: backend/src/round_robin/dispatcher/service.py:74-76
Trigger: A final-stage failure leaves a terminal, manually retryable run with unused finish funds; the user leaves it alone until the frozen provider configuration expires or becomes permanently unusable.
Finding: A retry-eligible synthesis failure intentionally retains the unused finish hold, but terminal runs are excluded from the ordinary reconciliation scan. The separate terminal scan only handles unfinished authorized attempts, so it never revisits an unused hold after the frozen provider configuration expires. Retry eligibility itself checks frozen active time and call counters, not configuration validity; terminal active time no longer decreases. The hold consequently remains charged against current owner and deployment windows even though the old run can no longer authorize work. In a real API-created live run with fake adapters, synthesis worker loss left a $.38 hold plus a $.02 unknown attempt. Two days later, the old configuration correctly failed with frozen_configuration_expired, but three reconciliation passes retained the $.38 hold. A terminal cancel did not release it. A new explicitly accepted run under a fresh valid configuration then failed owner_daily_budget_exhausted against a $.60 owner ceiling, although retaining only the legitimately unknown $.02 attempt and reserving the new $.40 finish pool would require $.42.

RR-026 [P2] Anonymous sign-in blocks the ASGI event loop during database contention
Location: backend/src/round_robin/security/hosted.py:123-127
Trigger: An ordinary competing transaction holds the deployment policy row when a hosted login starts.
Finding: OpaqueLoginState performs synchronous SQLAlchemy transactions and deployment-policy row locking directly inside its async ASGI entry point. An anonymous /auth/login request waiting for that normal shared database lock blocks the event loop, including otherwise unrelated requests and SSE timers handled by the same worker. The response-save callback also performs synchronous database work.
Evidence: {"probe": "probes/hosted_event_loop.py", "result": "evidence/hosted-event-loop-result.json", "observed": {"provider_calls": 0, "lock_hold_seconds": 1.0, "baseline_health": 200, "twenty_ms_heartbeat_seconds": 1.027, "concurrent_health": 200, "login_status": 307, "schema_cleaned": true}, "method": "Actual PostgreSQL row contention in a random owned schema, ASGI HTTP client, and local fake OIDC redirect. A 20ms heartbeat took 1.027 seconds while another thread held the lock for one second."}
Fix direction: Move complete blocking transaction phases off the event loop, or use an asynchronous database implementation. Preserve atomic quota reservation and login-state fencing. Apply the same discipline to the response-save callback.
Limits: This proves blocking of the affected ASGI worker during database waits. It does not establish an attacker-controlled indefinite deadlock, typical production latency, or an outage across multiple independent workers.

RR-027 [P2] Markdown export turns untrusted evidence into active image/HTML markup
Location: backend/src/round_robin/reports/exports.py:74-75
Trigger: Export a saved report containing Markdown images or raw HTML in source text, title, option label or generated summary.
Finding: report_markdown places exact uploaded/retrieved source text directly in a Markdown blockquote without escaping Markdown syntax or HTML. Prefixing a line with '> ' does not disable images or HTML. A supplier attachment containing ![supplier tracking pixel](https://tracking.invalid/supplier-pixel) and <img src="https://tracking.invalid/raw-html-pixel"> passes upload, preflight, the full simulated worker pipeline, saved-report validation, and export; the downloaded ready Markdown retains both as active markup. Titles, option labels and model summaries have the same interpolation problem. An image-capable Markdown preview can therefore fetch an attacker-selected remote image merely when the exported report is viewed; HTML-capable viewers additionally receive raw HTML. This is an export rendering-policy defect, not a claim that the application itself executed the image or script.
Evidence: {"command": "PYTHONPATH=backend/src:backend/tests:. .venv/bin/python probes/data-probe_exports_and_readiness.py", "probe": "probes/data-probe_exports_and_readiness.py", "results": "evidence/data-probe-results.json", "artifact": "evidence/data-export-unsafe-markup.txt", "observed": "HTTP meeting create 201; text upload ready; preflight blockers []; start 202; real simulated worker drain completed; Markdown export ready; download 200; four raw external image expressions retained, including two from uploaded supplier evidence.", "network_scope": "No external request or paid call was made. tracking.invalid is a synthetic inert destination."}
Fix direction: Escape untrusted text into inert Markdown literals (or render it with a consistent allowlisted policy), preserve exact bytes separately if needed, and prohibit remote images/raw HTML in report rendering.
Limits: The ready downloaded export preserved active markup; remote fetching depends on the downstream Markdown viewer. No external image was requested during this audit.

CAPABILITY LIMITATION — NOT COUNTED AS A CONFIRMED DEFECT

No production path currently makes cost evidence supported, so real ready_to_choose is unreachable
Every original cost component source_ref is rewritten to newly created structured evidence with verification_status=user_supplied. The cost dependency accepts only supported sources. The probe exercises real evidence preparation and real supported-claim persistence, then ideal positive distinct-provider review records: positive included costs and explicit included zero costs both pass all hard requirements yet remain conditional solely due to the unverified cost dependency. Excluded and not-applicable-only cases also remain conditional with their expected additional cost gaps. All four probes accept a supported fact claim without promoting source verification. No runtime evidence-verification mutation route was found.
Repository documentation consistently says entered costs are not independently verified and readiness requires accepted scoped support; it does not clearly promise that current functionality must let a user promote those sources. Treat this as a product capability limitation until an explicit supported-evidence acceptance workflow is required, rather than weakening the conservative readiness gate.
