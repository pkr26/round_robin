SESSION-E02 — P1 — An audit can close an objection using an answer from an obsolete synthesis
Origin: session_change_or_incomplete_integration
Source: backend/src/round_robin/research/discussion.py:17; backend/src/round_robin/research/discussion.py:45; backend/src/round_robin/research/discussion.py:91; backend/src/round_robin/research/discussion.py:100
Trigger: Synthesis0 answers a critical issue. A later replacement synthesis omits that answer or its required condition. Audit1 returns resolved for the issue.
Observed: The reducer accepts any prior answered event from a different provider if the frozen brief hash matches. It does not require the latest synthesis to answer, bind the answer/resolution to the current synthesis or claim versions, or reopen resolved issues on a replacement synthesis. The reproduced ledger closes the issue despite no response in synthesis1, and build_report returns ready_to_choose.
Impact: The new objection mechanism can certify an obsolete correction and hide a regression in the actual final recommendation. The main invariant that each current material concern gets an inspectable current resolution is not enforced.
Repair direction: Bind answers and reviewer resolutions to an explicit current synthesis ID, issue/claim versions and input packet hash. On replacement, carry or invalidate each resolution through an explicit recheck; require an answer in the current synthesis or an explicit verified carry-forward record before independent resolution.
Limit: The auditor does receive the latest synthesis in the live packet, so a careful model could avoid this. The defect is deterministic acceptance of a stale disposition, not proof every real auditor would make the mistake or a demand that the application prove natural-language truth.
Evidence: evidence/review.json; probe.py:stale_answer_resolution; probe-results.json:stale_answer_resolution. Events opened by proposal1, answered by synthesis0, resolved by audit1; no synthesis1 answer. New report ready_to_choose.

Consequences for the previous closure claims

E-F04, E-G01, RUNTIME-01, ROOT-01/02 and EVAL-01/02/03 need qualification at the new integration boundaries recorded in summary.json. Their repairs and regression tests exist, but those tests do not establish that every intended scenario is closed. This audit does not claim that all work was ineffective: independent proposals, due-time guards, scoped identities, conditional decisions, immutable raw reports and many existing controls passed their reviewed checks. No new defect was observed in several inspected responsibilities; that is not an absence-of-fault proof.

The obsolete-synthesis and quote-expiry issues are deterministic workflow acceptance gaps. They do not claim the application can prove semantic truth or that every live model would produce the bad sequence. The expiry case was additionally reproduced through a real authenticated owner API against a temporary completed fixture: a Nov17 requirement attestation returned 201 and produced ready report v7 while all cost receipts remained dated Oct28 and the quotes expired Nov10. Fixture labels/usage were synthetic and no paid model call occurred.

Markdown and PDF lose actual resolution events even though raw JSON and the UI retain them. A visually plausible export therefore cannot substitute for reference/event fidelity. The exported counter-basis omission is also noted in the domain review; the principal reproduced finding is disappearance of the resolution explanations.

The visual prompt failure was reproduced through the actual worker with an injected MockTransport: 0 HTTP requests, 1 consumed request/submission, 0.40 USD retained as unknown exposure. That is falsely unresolved conservative exposure, not a demonstrated external charge. The 80-blocker boundary preserves the findings and keeps the existing version readable; it fails to offer a usable next edit and has an uncaught route exception. The study-reference finding affects blinded reviewer output; private stage storage retains the claim definition.

The reporting-tool defect was reproduced on temporary copies of real successful logs and source. Source was changed to invalid Python after those logs; finalize.py then created a new manifest binding that source and marked all 17 closures verified. Its declarations about some checks are unconditional. This audit independently reran the current suites, so the existing 2014/250 results are confirmed. One subordinate evidence-lane source hash for claims.py is stale after the final claim-kind guard; the later root repair manifest correctly covers that current file. Root-manifest consistency and execution provenance are different properties.

Suggested repair order

1. Bind reassessment freshness to the new assessment date and invalidate expired cost support while preserving historical reports.
2. Bind objection answers/resolutions to the exact current synthesis, claim versions and packet; require explicit reviewed carry-forward after replacement.
3. Publish valid run/report state before independently loading history, retaining Stop and result access during activity failures.
4. Unify text/image capacity priority; run actual provider payload/context checks before accepting Start; move all pure visual prompt checks before authorization and classify provably unsent failures correctly.
5. Preserve full ledger/counter-basis content in exports, support bounded visual overflow with an explicit recoverable outcome, and include durable claim definitions in the blinded study reference closure.
6. Add assessment-read recovery, bind verification receipts to command exits and test-start source inputs, and repair fallback traversal without broadening any funding or retry ceiling.
