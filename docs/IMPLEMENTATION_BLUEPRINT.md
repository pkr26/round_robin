## Work that can start immediately

Prepare the fictional sample, draft/report schemas, prototype, simulated runner, validation fixtures and evaluation manifests without provider credentials or research participants. Use provisional fictional tasks and label them. Replace or validate them with recent real tasks before Phase 0 passes. External research and live funding are completion prerequisites for the study, not prerequisites for writing its offline tooling. Broad durable application construction remains gated on Phase 0.

The first implementation review contains a typed fictional decision brief, exact stored evidence, independently authored fixture contributions, a rendered comparison/readiness report, a changed-input example and tests for their important invariants. A fictional fixture is not evidence of model quality or user demand. Avoid building infrastructure unrelated to these artifacts.

## Typed contracts and bounds

Python schemas under `backend/src/round_robin/schemas/` are authoritative. Export OpenAPI, event JSON Schema and generated TypeScript/runtime validation. All mutations carry an owner-scoped command UUID and an expected resource revision where applicable. IDs are server-issued opaque identifiers; clients cannot choose owners, storage keys or authoritative evidence IDs. Dates/times use ISO 8601 with UTC offsets; accounting uses UTC. Money/quantities are finite decimal strings on JSON boundaries, never binary floating point, NaN or infinity. Reject unknown command fields and invalid enum values.

| Contract / proposed schema | Required data and validation |
| --- | --- |
| `DraftBrief`, `schemas/briefs.py` | Revision, title, question, goal, currency, budget, deadline/timezone, explicit cost horizon, options, hard requirements, ranked preferences, user facts, attachment selection, public-research scope. Incomplete drafts may save; preflight identifies blockers. |
| `Option`, `CostComponent` | Server ID, label, provenance; component kind, decimal amount or explicit unknown, currency/unit, quantity, frequency, horizon, quote validity, source/input reference, included/excluded/not-applicable status. Zero must be explicit; unknown is null with reason. |
| `Constraint`, `ConstraintResult` | Stable requirement ID, supplied/assumed origin, typed operand/operator when deterministic, result `pass/fail/unknown/not_applicable`, basis references, assessor/method, and applicability reason. Free text does not become executable code. |
| `Preflight`, `schemas/preflight.py` | Draft revision, immutable selected-input manifest, shared recipient set, approved public terms/templates, protocol/model/prompt/schema/pricing versions, limits, finish policy, fingerprint, expiry/admission deadline and `consumed_by_run_id`. One preflight authorizes at most one run. |
| `EvidencePassage`, `Calculation`, `schemas/evidence.py` | Owner/run/source-version identity, exact passage locator/hash and scope; or typed calculation inputs/formula/units/horizon/rounding/output. A user assertion remains labeled user-supplied rather than independently verified. |
| `Contribution`, `schemas/contributions.py` | Stage/role, public rationale, response-local claim aliases, existing reference IDs, constraint results, assumptions, objections, responses and limits. No hidden reasoning is requested. |
| `DecisionReport`, `schemas/reports.py` | Version/event cutoff, validated recommendation or explicit no-choice/unavailable reason, readiness/reasons, comparison, essential dependencies, dissent, next-evidence items, usage/coverage and stopping reason. Render every format from this object. |
| `RunSnapshot`, `EventEnvelope`, `schemas/events.py` | Schema version, run/revision, committed sequence/event type and bounded typed payload or record reference. A snapshot has an event cutoff and paginated references; it does not require downloading the entire history. |

Initial core limits are configuration values to test, not provider capabilities. Question: 4,000 characters; background: 12,000; two to four confirmed candidate options plus at most one status-quo baseline; 20 hard requirements; ten ranked preferences; 30 cost components per option; five text attachments under the existing one-MiB/file and five-MiB/meeting limits. Cap a single requirement/preference description at 500 characters and public research at eight explicitly approved terms of 120 characters each. Reject oversized JSON before parsing at 128 KiB, excluding the separate upload route. These limits do not require every draft field to be filled.

Limit structured contributions to 20 new claims, 12 material objections and 40 existing references per response. Source packets contain at most 24 selected passages of 2,000 characters each within the existing eight-page/six-query fetch allowance. Preserve source provenance; a bounded excerpt is not a full-document guarantee. Initial output-token caps are intake 2,048, proposal 3,072, critique 1,536, revision 2,048, synthesis 4,096 and audit 2,048. Include provider-specific billable reasoning/output exposure in the adapter's conservative bound; an unsupported bound blocks paid authorization.

`orchestration/context.py` deterministically assembles the frozen brief and essential dependencies first, then scoped claims/passages. Use the configured endpoint's context ceiling and a verified conservative token estimator, retaining the output allowance. Fit by removing optional history and deduplicating, not by silently dropping requirements or evidence qualifications. If essential material cannot fit, request a narrower brief or publish the limitation. A model summarization is a separately authorized inference, never a hidden context-management call. Test bounds on actual serialized requests, not just individual form fields.

## Preflight, Start and immutable consent

1. `POST /api/meetings/:id/preflight` runs deterministic validation and pricing/capability checks without inference. It saves a preflight ID and canonical fingerprint, the exact draft revision/attachment hashes/public scope, selected protocol and three configured providers, and displayed limits. Unknown measurement data stays unknown. Preflight is valid for ten minutes before Start. Initial admission must occur within 30 minutes after accepted Start; show this before authorization.
2. `POST /api/meetings/:id/runs` receives `preflight_id`, `expected_draft_revision` and command UUID. In one transaction, resolve duplicate command identity, lock/check owner/draft/input readiness, compare preflight/configuration, enforce quotas, consume preflight and save the immutable run, manifest, command outcome, first work and outbox records. Enforce a unique accepted run per preflight. The same command returns its original result; a different command using a consumed preflight conflicts without new work. Intentional repetition needs a new preflight. Stale/expired preflight dispatches nothing. No model request occurs inside the HTTP transaction.
3. Queue admission rechecks expiry, ownership, compatible frozen capabilities/prices, current lower spending policies, deletion/epoch and capacity, then reserves the finish pool. Store `first_admitted_at`; the 30-minute gate applies only while it is null. Expired first admission produces a saved no-spend terminal result with `admission_expired`; retry requires a new explicit preflight/Start or linked run. Replays never renew the deadline. A configuration change cannot silently replace a model, add a recipient or raise an allowance. If the frozen conservative bound is no longer supported, block affected work visibly.
4. Each dispatch rechecks the same scope and current spending lock. Changed health can cause the recorded failure/fallback policy; it cannot rewrite the accepted configuration. After acceptance, expiry of the preflight itself does not cancel a healthy admitted run; its admitted-time and input-wait policies apply.

Preflight distinguishes hard blockers from intake-resolvable warnings. Invalid ownership, unsupported prices/capabilities, forbidden recipients, unreadied files, malformed/oversized fields, expired configuration and absent spending bounds block Start. Missing options, preferences or quote details may admit one explicitly disclosed intake/confirmation step within the same funded limits. Two to four confirmed options are required at resolved-brief freeze before proposals, not for saving a draft or requesting intake help. A contradiction unresolved by confirmation stops dependent work; a warning cannot silently become an established fact.

The provisional Standard path is intake → optional input confirmation → initial evidence → three independent proposals → synthesis → distinct audit → publication. Debate is inserted only when enabled by evaluation. Keep the same logical-step keys and existing two-call ceilings.

Intake has one committed successful result: a proposed normalized brief and at most three questions in one batch. A schema repair can consume the same step's remaining call; a successful intake is never called again after an answer. Material normalization, missing options or clarification uses `awaiting_input`; expected-version user confirmation deterministically creates the resolved brief and freezes it. All confirmed comparisons contain two to four options plus the applicable baseline. Unknown answers remain explicit; critical gaps produce conditional/no-choice output rather than more intake calls. Input wait expires after 24 hours with `input_expired` and does not hold active admission. Accepted confirmation or an eligible manual retry creates one 30-minute resumption-admission ticket bound to its command UUID; replays cannot renew it. Requeue checks this ticket, original eligibility and remaining active time, not the already-satisfied initial deadline. It reuses the remaining finish pool and original step/call limits. Expired tickets never continue automatically; new work needs an eligible explicit retry or linked run.

## Privacy, uploads and lineage

Use one shared three-provider recipient set for all selected content in a core run, including derived peer messages, synthesis, audit and declared fallback. Reject selection of an attachment that cannot be sent to any one of those providers. Do not offer per-provider confidentiality controls without derived-data scope propagation. Search has a separate public scope and receives none of these private packets.

Only the user-approved public terms and public region may enter search. The controller renders allowlisted query templates from their immutable IDs; models can request term/template IDs, not arbitrary query strings. URLs to fetch must be registered user-approved public URLs or server-recorded discovery candidates. A model-generated URL alone is not a fetch authorization. Preview public terms before Start; if they are inadequate, retain a gap or create an explicitly updated run. Filtering arbitrary model text is defense in depth, not the privacy boundary.

Public evidence retrieval rejects credentials and secret-bearing URLs. Later signed image-job download locators are different: a private adapter may fetch a locator bound to a known authorized provider job through configured provider destinations and the same network/size protections. Never copy its tokens into source records, browser links, logs or exports. No endpoint accepts a user-selected arbitrary private fetch host.

Uploads use `temporary → ready → purged` with failed validation remaining unusable. Reserve storage before reading bytes; validate UTF-8/type/limits, normalize only documented text encoding/line endings, and hash exact canonical bytes on the server. Only ready immutable records owned by this meeting may enter Start; the client cannot forge a checksum or object key. Clean abandoned temporary uploads after one hour. Provider packets use the frozen canonical bytes. Removing a draft selection changes future use, not historical records.

All follow-up runs stay in the same owner-scoped meeting. Cross-meeting private imports and cross-owner caches are deferred. `research/reuse.py` validates selected parent items and commits a child `ReuseManifest`: child-scoped claim/source/calculation IDs mapped to approved immutable parent versions/hashes. Models and child routes use only child IDs; arbitrary parent IDs remain invalid. Preserve origin and original verification dates, and recheck time-sensitive evidence before accepting it for the new decision. Immutable bytes may be referenced within the meeting instead of physically copied; logical ownership/import membership remains explicit. Refresh creates a new version. Meeting deletion purges all runs/derivatives under the restore manifest. Public caching across runs is deferred until its refresh/deletion behavior is tested.

## Claim identity, calculation and readiness

Models use local aliases such as `new_claim_1` for new propositions and server-issued IDs for existing claims/passages. `research/claims.py` validates uniqueness/references, then the commit transaction assigns persistent IDs and rewrites same-response references atomically. Unknown or cross-run authoritative IDs fail validation. The immutable contribution keeps alias-to-ID provenance. Revisions create new claim versions with predecessor IDs; they cannot overwrite what a source supported earlier.

`research/calculator.py` accepts an allowlisted typed operation, plain decimal strings, units, horizon and input references. Reject exponent notation, strings over 32 characters, more than 18 significant digits, nonfinite numbers, zero divisors and out-of-range operands before arithmetic. Initial bounds: monetary components 0–10^12 with at most six decimal places; quantities 0–10^9 with six places; conversion rates strictly positive through 10^6 with at most 12 places; horizon an integer 1–120 months. Represent discounts as an explicit subtracting component, not an unvalidated negative quantity. Allow at most 120 operands, operation depth four and intermediate magnitude 10^30. Use Decimal precision 64 with recorded context/flags; reject unsupported inexact add/multiply/subtract intermediates, and explicitly record bounded division/final currency rounding rather than promising unlimited exact precision. Trap overflow/invalid operations and cap serialized output. No `eval`, generated Python or arbitrary formulas. Unit conversion is allowlisted; exchange rates need a dated basis. Compare common horizons/component rules. Known subtotals may display beside an unknown total with its missing components.

Fictional regression fixture: A has USD 1,000 upfront + USD 50/month; B has USD 1,600 upfront + USD 20/month. At 12 months totals are 1,600 and 1,840; equality is at 20 months, with A cheaper before and B after. If B's required installation cost is unknown, its all-in total is unknown and this example cannot establish the cheapest option. These are test numbers, not quotes or market estimates.

`reports/readiness.py` derives published readiness from validated structured assessments and coverage rather than copying a model label:

| Condition | Published result |
| --- | --- |
| No valid synthesis/assessment exists | Null readiness and explicit unavailable/pending reason; deterministic partial report preserves prior work |
| Every considered applicable option has an established hard disqualification | `no_feasible_option`, listing each disqualification; unknown alone cannot establish this |
| No defensible preferred option or feasibility basis can be established | `insufficient_evidence`, listing the decisive missing facts/preferences |
| A preferred option remains plausible but has a decisive assumption, unresolved objection or missing required audit | `conditional` with its exact dependencies/review limitation; never an unqualified ready label |
| Valid synthesis and successful distinct audit, no unresolved critical defect, selected option passes all applicable hard requirements and essential dependencies have accepted scoped support | `ready_to_choose` within the recorded scope; user-supplied facts retain their origin and limitations |

An audit finding a substantive defect blocks ready publication even when all IDs resolve. Code can validate identity, calculations, scope and gate inputs; semantic support/requirement assessments remain attributable model/human judgments that need evaluation. Do not advertise this reducer as a proof of real-world correctness. Preserve no-choice, unavailable recommendation, disagreement and actual review coverage across all exports.

## Budget ledger and finish conversion

Every paid operation has an immutable authorization identity, owner/deployment/run-or-diagnostic scope, conservative exposure, configuration version, UTC authorization-period IDs and usage certainty. Model inference consumes the 24-call/two-step-call counters; billable retrieval/status operations use their own declared transport counters and the same monetary gateway. Provider SDKs cannot hide retries or tool follow-ups. Connection tests are explicit bounded diagnostic operations, never health checks.

Within an applicable spending window, exposure is the sum of settled charges authorized in that window, each distinct unsettled attempt's conservative bound, and unused finish holds. Carry older unsettled attempts into the current window once; do not count the same attempt as both an active reservation and a second unknown charge. Run totals retain all its charges/exposure. Reconciliation uses provider final usage when available, records discrepancies and preserves overrun rather than clipping it. Confirmed settled charges stay attributed to their authorization window. Acknowledged higher costs block further spending when a ceiling is exceeded.

Reserve the mandatory synthesis/audit monetary finish pool once at admission against run, owner and deployment headroom. On final-stage dispatch, atomically transfer the designated part of that pool into an attempt reservation; do not charge both. Unused finish money releases on deterministic terminal settlement. Unknown attempt exposure does not. Protect two mandatory inference slots and the sequential bounded final-stage time plus persistence margin from optional work. A retry/repair/correction requires its own remaining resources; the finish pool does not grant extra calls. Skipping optional work is preferred to producing an unfunded ending.

Acquire conflicting financial locks in one order everywhere: deployment policy/buckets → owner buckets → run → logical step. Policy/kill-switch mutations use the same ordering. Period rows are created idempotently; policy changes cannot reduce recorded exposure or raise accepted per-run limits. No network request occurs while holding those locks. Result transactions preserve the same order when reconciling money and writing ordered events.

A conservative operator booking can close an accounting task, but cannot make an unverified request become final provider usage or remove its unresolved carryover. Only a confirmed final settlement releases that uncertainty. Otherwise it stays counted after rollover and restoration, with manual escalation. This deliberately prefers blocked new work to silently renewed unknown liability.

Phase 0 uses the same policy functions with one exclusive process/file lock, an append-only fsynced local journal and batch/owner/deployment caps before dispatch. The budget journal is the operator/deployment's configured authoritative path across batches, not a newly empty scratch file per experiment. Refuse a second writer or missing/corrupt expected history. Restart reconciles the journal first; authorization without a durable outcome remains possibly sent and is not automatically repeated. Paid evaluation may not bypass the policy because PostgreSQL is not yet implemented.

## Commands, APIs and UI behavior

Retain minimal tombstones for resource-creating/paid command UUIDs for the owner namespace lifetime: keyed request fingerprint, outcome and noncontent resource references. A replay after meeting deletion returns gone and never creates new work. Do not expire a Start key and treat it as fresh. Draft-command compaction is allowed only while revision compare-and-set still prevents old edits taking effect. Namespace rotation after account deletion must not authenticate old sessions/commands; remove content-bearing results under the deletion policy.

Use explicit error codes including `draft_conflict`, `preflight_stale`, `preflight_expired`, `admission_expired`, `input_expired`, `input_scope_invalid`, `context_limit`, `quota_exceeded`, `spending_locked`, `finish_resources_unavailable` and `command_resource_gone`, with the existing structured retry scope/command certainty. Client state keeps unsaved edits separate from confirmed server data; old autosave responses cannot overwrite a newer local edit. Losing a connection changes connection status, not the saved run status. Reconcile pending command UUIDs before exposing another Start.

Create separate UI states for editable draft, unsaved/save-failed, preflight-blocked/expired, queued, running, awaiting-confirmation, stop-unconfirmed, cancelled, completed/limited, report-pending, export-failed and deleted. A ready Overview is not inferred from a spinner finishing. In comprehension tests, ask for the recommendation **or why a choice cannot yet be made**, the principal caveat, exact support and next action. No-choice can be the correct useful result.

## Evaluation records and measurement

Phase 0 fixed-evidence evaluation has 16 task cases across the five declared strata. Choose five before execution for three total executions each, including their original; the other 11 run once. This is 26 trials per workflow and 78 across three workflows. The primary 80% gate is at least 13 of 16 preregistered primary outputs scoring 4/5; repetitions measure variability and never replace poor originals or inflate independent sample size. Retain repeated critical defects in the release decision. At 24 requests/trial, the evaluation ceiling is 1,872 inference requests; at $2/trial its mathematical maximum is $156, not funding authorization. Allow at most three separately counted smoke requests, producing a combined upper request bound of 1,875. Actual batch currency/request limits and aggregate policies may be lower; stopping early yields an incomplete study, not an invented pass.

Phase 5 freezes 48 held-out end-to-end cases: eight each for budget/lifecycle costs, deadline/hard constraints, missing/stale inputs, preferences/status quo, misleading/shared evidence, and clarification/tool/provider limitations. Expected limited outcomes are scored for honesty/usefulness, not forced into a purchase recommendation. Separate deterministic injected outages from ordinary latency results, and label their profile. Do not tune on held-out failures and keep citing the same set as held out. Its retrieval/privacy/version behavior is tested through the actual application; the Phase 0 checked-snapshot study alone cannot establish that quality.

Store `task_id/version`, dataset/configuration fingerprints, primary/repeat index, workflow arm, prompt/model/pricing versions, input/evidence IDs, output hash, authorized work/ledger, timestamps, failures and randomization token. Human packets contain task criteria, evidence and randomized output without arm/provider identity. Each grading record has reviewer identity, hard-constraint findings, passage-support findings, critical-defect reason, usefulness 1–5, next-action judgment and timestamp. Save original independent ratings and adjudication reasons; do not replace them with a model-judge score.

Instrument `run.admitted`, `content.committed`, `report.published` and active-interval boundaries without private content. A report publication after a missing audit is not successful completion of mandatory work. Primary latency gates mean at least 90% of admitted ordinary-profile trials have qualifying content within 60 active seconds, at least 50% complete within 120, and at least 90% complete within 300. Failed, cancelled or absent outcomes are misses; also show their categories and all wall-clock queue/input waits. Report successful-run nearest-rank percentiles separately with sample size. These attainment rates implement the existing p90/p50 targets without hiding failures inside an undefined percentile calculation.

## Operations and first deployment profile

Keep operators on a CLI/config surface, not a new administration product. Implement `python -m round_robin.ops` entry points for `config-check`, `spend-lock`, `usage-inspect`, `usage-reconcile`, `purge-inspect`, `backup`, `restore-verify` and `drain`. These are proposed commands, not runnable today. Require operator authentication/access, explicit environment identification, noncontent audit records and fail-closed production checks. Reconciliation references evidence and cannot delete ledger history. Paid access begins locked until configuration/capability/pricing validation succeeds.

Initial bounded personal/pilot defaults: one executing run globally; three queued runs per owner and 20 globally; three awaiting-input runs per owner; FIFO admission with owner quota checks; one active export and at most two pending exports per owner/five globally. Expired runs settle before admission. Retained owner artifacts are capped at 100 MiB, one export at ten MiB, meeting count at 100, and event payload at 16 KiB with references to paginated content. Reject or offer explicit cleanup at quota; do not erase old reports automatically or start new inference. Hosted deployments must explicitly configure these values and spending quotas even when using the initial defaults. Visual assets need a separately reviewed storage profile before enablement.

Local development identity requires explicit development mode, loopback-only services and rejected external Host/Origin/proxy exposure; production mode never activates it. Hosted authentication uses Authlib with one configured OIDC issuer, authorization-code flow with PKCE/state/nonce validation, and server-side opaque sessions. Identity is `(issuer, subject)`, not an editable email. Invitation is an operator allowlist entry; unlisted identities get no paid access or account-data access. Cookies are Secure/HttpOnly/SameSite=Lax with CSRF checks for mutations; initial sessions have 30-minute idle and 12-hour absolute expiry. Revocation closes protected SSE delivery at the next authorization/heartbeat boundary and blocks commands immediately; already delivered bytes cannot be recalled. Never implement token verification by hand.

Hosted startup fails closed for missing sessions, owner isolation, private storage, provider/funding policy, explicit quotas, allowed origin, retention or deletion-manifest configuration. Verify configuration without paid health requests. Apply migrations once before compatible API/workers become ready; test additive schema compatibility and old-report read adapters. A rollback may restore supported application binaries, not replay paid work or roll the database back past newer accounting/deletions.

Initial retention profile: reports and source history persist until explicit meeting deletion or a clearly agreed retention setting; temporary uploads expire after one hour; regenerable export files after seven days; noncontent operational logs after 14 days. Target active-storage purge within 24 hours after immediate access revocation, exposing pending/failed purge honestly. Back up database plus referenced assets daily, retain snapshots seven days, and store the current deletion manifest independently. Proposed pilot recovery targets are at most 24 hours of backup data loss and four hours to safe restoration; neither is achieved until a timed synthetic restore proves it. Restore starts with reads/dispatch closed, reapplies the complete deletion manifest, fences old execution, quarantines paid work and reconciles accounting before access. A seven-day backup window is disclosed, not a claim of immediate backup erasure.

## Primary implementation references

Use [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) for row-local checks, unique keys and foreign keys, with transactions/locking for cross-row accounting rather than assuming a check constraint serializes a budget. [Pydantic strict validation](https://docs.pydantic.dev/latest/concepts/strict_mode/) and [serialization](https://docs.pydantic.dev/latest/concepts/serialization/) inform the explicit typed JSON boundary. [Python Decimal](https://docs.python.org/3/library/decimal.html) supplies controlled precision and rounding; the typed-operation restrictions above remain application policy. [Celery task documentation](https://docs.celeryq.dev/en/stable/userguide/tasks.html) explains why acknowledgment/retry configuration must be tested with real workers. [Authlib](https://authlib.org/projects/authlib/) supports the selected OIDC client approach; application sessions, invitations and ownership still need implementation and verification. Pin compatible supported versions when scaffolding rather than treating these live documentation URLs as a dependency lockfile.
